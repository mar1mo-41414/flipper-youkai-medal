# 仕組み

## パスワードと暗号の算出

どちらのゲームも、タグの UID (7 バイト) だけから次のように算出している。

```
h1   = HMAC-SHA256(KEY1, UID 7 バイト)
h1'  = h1 の各バイトの上位/下位ニブルを SBOX で置換
h2   = HMAC-SHA256(KEY2, h1')
PWD  = h2[28:32]      … PWD_AUTH (0x1B) で送る 4 バイト
PACK = BE EF          … ゲームが期待する応答
保護データ: AES-128-CTR
  key = h2[0:16]
  IV  = (h2[24:32] || UID || 00) XOR (h2[0:15] || 00)
  48 バイト = 16 バイト x 3 ブロック。各ブロックの最終バイトは先頭 15 バイトの和 (mod 256)
```

| | KEY1 | KEY2 | SBOX | 保護データ |
|---|---|---|---|---|
| 妖怪ウォッチ3 (3DS) | `SjqjE90z8w` | `bYYw75Ks9K` | 14,2,11,7,5,0,12,8,10,13,15,4,6,3,1,9 | ページ 6〜17 |
| 妖怪ウォッチ4 (Switch) | `DKtjn3JAZc` | `5g9D63n8Mt` | 4,9,15,0,5,10,14,1,6,11,13,2,7,12,3,8 | ページ 28〜39 |

妖怪ウォッチ4 の算出式と、ゲーム内部の処理の解析は
[switch-youkaiwatch4-medal](https://github.com/mar1mo-41414/switch-youkaiwatch4-medal) を参照。

### 妖怪ウォッチ4 の平文

先頭 7 バイトが ASCII で `NNNNXXX`。

- `NNNN`: シールに印刷されている番号 (例 `A315` → `0315`)。`int(XXX, 36) − 28652` と一致する。ゲームは使っていない
- `XXX`: アークの種別 ID (36 進 3 文字)。ゲームはこれでアークの種類を決める

残りは 0 (とチェックサム)。

## 種類の自動判別

認証の前にページ 0〜3 を読み、ページ 3 (NDEF の Capability Container) で判別する。

- `F5 10 ..` → 妖怪ウォッチ3 のメダル (ページ 4 は `BABO`)
- `E1 x1 .. x F` → 妖怪ウォッチ4 のアーク

アークの CC は `E1 11 12 0F`。工場出荷の NTAG は `E1 10 12 00` (213) / `E1 10 3E 00` (215) なので、
**バージョンのニブル (1.1) とアクセス条件 (`0F` = NDEF 書き込み不可) まで見る**。
先頭の `E1` だけで判定すると、NDEF 初期化済みの普通の NTAG を全部アークとして拾ってしまう。

さらに **YW4 では NDEF (ページ 4) が残っているかも確認する**。ページ 3 の CC は WRITE が
ビット OR で元に戻せないので、Erase で消したタグにもアークの CC が残り、ページ 3 だけでは
消去済みと区別できないため。ページ 4〜7 は AUTH0 = `0x1C` の範囲外なので認証なしで読める
(YW3 は AUTH0 = 6 でページ 6 以降が保護されるため、この確認は YW4 だけに使う)。

## 読み取りの流れ

`nfc_poller` (MfUltralight) を使う。

1. `AuthRequest` イベントで UID を取得し、(Auto のとき) `mf_ultralight_poller_read_page(0)` で種類を判別
2. パスワードを計算して `auth_context.password` にセット
3. poller が全ページを読む → `ReadSuccess` で結果をコピー
4. 保護データを復号してチェックサムを確認
5. PWD / PACK をページ 43 / 44 に書き込んでから `nfc_device_save` で保存
   (標準の NFC アプリでパスワードを入れて解除・保存したファイルとバイト単位で同じになる)

## 複製・種類の変更

1. 復号した平文を用意する (Change ID のときは `NNNNXXX` + 0 で作り直す)
2. 新しい UID = `04` + 乱数 6 バイト
3. ページ 0〜2 の UID / BCC0 (`88 ^ UID0 ^ UID1 ^ UID2`) / BCC1 (`UID3 ^ .. ^ UID6`) を書き換え
4. チェックサムを付けて、新しい UID の鍵で暗号化し直す
5. PWD / PACK を書き込んで保存

NDEF の URL と NXP の署名 (READ_SIG の値) は元のまま残す。妖怪ウォッチ4 はどちらも確認していない
(実機で確認済み)。

## 元ダンプなしでアークを作る

ゲームがアークの種類を決めているのは保護データの中の 36 進 3 文字の種別 ID だけで、保護データは
UID から算出した鍵で暗号化するだけなので、ダンプ 1 枚を 1 から組み立てられる。

| ページ | 値 | 出どころ |
|---|---|---|
| 0〜2 | UID (`04` + 乱数 6 バイト) / BCC / internal `48` / ロックバイト 0 | 計算 (`rebuild_with_new_uid`) |
| 3 | `E1 11 12 0F` | 実物と同じ固定値 |
| 4〜26 | NDEF: `https://www.ywg.jp/<ID>` | 合成 (後述) |
| 27 | `BA B0 01 01` | 実物と同じ固定値 |
| 28〜39 | 保護データ (平文 = `NNNN` + ID + 0 埋め + チェックサム) | UID の鍵で暗号化 |
| 40 | `00 00 00 BD` (動的ロック。`BD` は RFUI の初期値) | 固定値 |
| 41 / 42 | `04 00 00 1C` / `C0 00 00 00` | 実物と同じ固定値 |
| 43 / 44 | PWD / PACK (`BE EF`) | UID から算出 |

`.nfc` にはページ以外も入るので、エミュレートに必要な分も埋める。

| 項目 | 値 |
|---|---|
| 種類 | NTAG213 (`pages_total` = 45、`pages_read` も 45) |
| GET_VERSION | `00 04 04 02 01 00 0F 03` |
| ATQA / SAK | `44 00` / `00` |
| 署名 / カウンタ / tearing flag | 0 |

GET_VERSION の値は、ファームの `mf_ultralight_get_type_by_version()` が NTAG213 と判定するものと
一致させてある (`storage_size` = `0x0F` かつ `prod_type` の下位ニブルが 4 = NTAG。
下位ニブルが 3 だと Ultralight AES と判定されてしまう)。
ATQA の下位バイト `0x44` は UID が 7 バイトであることを表す。

実機で確認済み: 0 から作ったアークが、Flipper Zero でのエミュレートでも、空の NTAG に焼いた
物理タグでも、妖怪ウォッチ4 にそのまま読み込まれた。下記の「作れないもの」がどちらも
問題にならないことが裏付けられた形。

### 作れないもの

**NXP の署名 (READ_SIG の値)**。タグの UID に対する NXP の秘密鍵の ECC 署名なので偽造できない。
0 のままにしている。ゲームは READ_SIG を送らないので影響しない (解析で確認済み)。
物理タグに書き込む場合は、そのタグ自身の本物の署名が残るのでそもそも関係ない。

**NDEF の URL トークン**。先頭 3 文字が種別 ID なのは分かっているが、残りの生成規則は不明。
`https://www.ywg.jp/<ID>` を NDEF の URI レコード (前置コード `0x04` = `https://`) として合成している。
ゲームは URL を読まない (UID と種別 ID を変えても読み込めることを実機で確認済み) ので影響しない。
NDEF を空にしない理由は、**種別判定が「NDEF が残っていること」も条件にしている**ため
(消去済みのタグを弾くための条件。「種類の自動判別」を参照)。

## 空の NTAG への書き込み

タグの UID は書き換えられないので、**かざしたタグの UID で鍵・PWD を算出し直してから**書き込む
(選んだ `.nfc` の UID は使わない)。1 枚の `.nfc` から UID の違うタグを何枚でも作れる。

`nfc_poller` の `AuthRequest` イベントの中で (= タグが起きていて、poller がまだ全ページ読み取りを
始めていない状態で) 一連の処理を同期的に行う。`mf_ultralight_poller_write_page()` /
`mf_ultralight_poller_read_page()` / `mf_ultralight_poller_auth_pwd()` はコールバックの中からしか
呼べないため。読み取り側の自動判別が同じ場所で `read_page` を使っているのと同じ理屈。

1. タグの種類が NTAG213 / 215 / 216 のどれかを確認する (`writable_tag_type`)。
   UID は 7 バイトであること
2. ページ 0〜3 を読んで静的ロックバイト (ページ 2 の 3・4 バイト目) を確認。
   このページ 0〜3 は書き込む内容の土台にも使う
3. 設定ページを読んで動的ロックバイトを確認する。保護されていれば UID から算出した PWD で解除する
   (このアプリで書いたタグなら通る)。認証と READ の順番には制約があるので、
   後述の「PWD_AUTH を送る順番」を参照
4. 書き込む内容を `app->out` に組み立てる (`build_write_data`)。土台はかざした実タグ
   (種類・バージョン・署名・ページ数・UID) で、そこに元ダンプのページ 3〜39 を載せ、
   保護データはそのタグの UID の鍵で暗号化し直す。PWD / PACK / 設定は、そのタグの種類の位置に置く
5. 書き込む: ページ 3〜39 → PWD → PACK → ACCESS → **CFG0 (AUTH0) を最後**。
   AUTH0 を先に書くと以降のページが保護されて PWD も設定も書けなくなる
6. 書いた PWD で PWD_AUTH して PACK (`BE EF`) を確認し、ページ 3〜39 と設定ページを読み戻して照合
7. 成功したら `app->out` を `app->data` に引き継ぎ、書き込んだ内容と同じダンプを
   `SD:/nfc/yokai/` にも保存する

### タグの種類ごとのページ

保護データ (ページ 3〜39) の位置はどの種類でも同じだが、設定・PWD・PACK・動的ロックの位置は違う。
ページ番号はファームの `mf_ultralight_get_config_page_num()` / `_get_pwd_page_num()` から取る。

| 種類 | 総ページ | CFG0 | ACCESS | PWD | PACK | 動的ロック |
|---|---|---|---|---|---|---|
| NTAG213 | 45 | 41 | 42 | 43 | 44 | 40 |
| NTAG215 | 135 | 131 | 132 | 133 | 134 | 130 |
| NTAG216 | 231 | 227 | 228 | 229 | 230 | 226 |

実物のメダル / アークは NTAG213 だが、**NTAG215 は実機で確認済み** (書き込み → 読み戻し照合 →
標準の NFC アプリ + `.fal` での読み取り・復号 → 妖怪ウォッチ4 での読み込みまで成功)。
NTAG216 はページ構成が NTAG215 と同じなので同様に動くはずだが未検証 (結果画面に注記を出す)。

NTAG215/216 ではメダルが使わないページ 40 以降は空のまま残す。NTAG213 ではそこが設定ページなので、
ゲームが読むページ 0x00〜0x2A のうち 40〜42 だけが NTAG213 と違うことになるが、
ゲームがこの領域を参照していないことは実機で裏付けられた (解析どおり)。

### 書き換えないもの

ページ 0〜2 (UID / BCC / 静的ロックバイト) と動的ロックバイトのページ。ロックをかけないので
同じタグに何度でも書き直せる。`CFGLCK` (設定ページの永久ロック) も立てない。
NXP の署名は空タグのものが残るが、妖怪ウォッチ4 は READ_SIG を送らないので問題にならない。

ページ 3 (NDEF の CC) は WRITE がビット OR になるタグがあるので、「今の値 + 元ダンプの値」を
書き込む値 = 期待値として扱う。こうすると OR のタグでも普通に上書きされるタグでも結果が同じになり、
読み戻しの照合がそのまま使える。工場出荷の NTAG215 (CC = `E1 10 3E 00`) ではサイズのバイトが
`0x3E` のまま残るが、種類の判別 (先頭が `E1`) もゲームの動作も NDEF を見ないので影響しない。

## PWD_AUTH を送る順番 (書き込み・消去の共通の注意点)

**PWD_AUTH は活性化してから最初に送らないと通らない。** 保護されたページを READ すると、タグは
NAK を返して IDLE 状態に戻り、以降のコマンドに応答しなくなるため。読み取りが動くのは、poller が
活性化直後に PWD_AUTH を送っているから。

やっかいなのは、**保護されているかどうかは設定ページを読まないと分からないのに、その設定ページ
自体が保護対象**という点 (`AUTH0 = 0x1C`、`ACCESS = 0x80` で読み出しも保護されている)。
先に READ すると認証できなくなり、先に認証すると空のタグで失敗して同じことになる。

そこで `prepare_tag_op()` は、その処理でありふれた方に賭けて順番を決め、外れたら poller を
作り直して 1 回だけ逆の順でやり直す (`app->wr_retry`)。

| 処理 | 1 回目 | 2 回目 (やり直し) |
|---|---|---|
| 消去 | 認証してから読む (対象はこのアプリで書いた = 保護されたタグ) | 認証せずに読む |
| 書き込み | 認証せずに読む (対象は空のタグ) | 認証してから読む |

ページ 0〜3 は AUTH0 (YW3 は 6、YW4 は 0x1C) の範囲外なので、保護されていても読める。
静的ロックバイトの確認と、消去での種別判定 (ページ 3) はここで行う。

これで次のどのケースも 2 回以内に決着する。

| ケース | 結果 |
|---|---|
| 書き込み: 空のタグ | 1 回目で成功 |
| 書き込み: このアプリで書いたタグへの上書き | 2 回目 (認証あり) で成功 |
| 消去: このアプリで書いたタグ | 1 回目で成功 |
| 消去: 保護されていない (書き込み途中で離れた) タグ | 2 回目 (認証なし) で成功 |
| 別のパスワードがかかったタグ | 2 回目で `WriteProtected` |

## 書き込んだタグの消去

書き込みの逆。`nfc_poller` の `AuthRequest` の中で同期的に行う点と、種類・UID・ロックビットの確認と
保護の解除 (`prepare_tag_op()`) は書き込みと共通。違いは次の 2 点。

- 消去では PWD をタグ自身から決めないといけないので、**ページ 3 で YW3/YW4 を判別してから**
  UID で PWD を計算する (書き込みでは元ダンプから種類が分かっている)
- 書き込む順番が逆。**保護を外すのを最初にやる**ので、途中でタグが離れても
  「中身が消えた上に保護がかかったまま」にならない

| 順 | ページ | 書く値 |
|---|---|---|
| 1 | CFG0 | `04 00 00 FF` (AUTH0 = FF = 保護なし。`04` は STRG_MOD_EN の初期値) |
| 2 | ACCESS | `00 05 00 00` (PROT・CFGLCK なし、VCTID = 05) |
| 3 | PWD / PACK | `FF FF FF FF` / `00 00 00 00` |
| 4 | ページ 4〜39 | `00 00 00 00` |

工場出荷値はデータシートの初期値。CFG0 の `04` (STRG_MOD_EN) は、実物のアークの CFG0 が
`04 00 00 1C` で、メーカーが AUTH0 だけ変えていたことからも裏付けられる。

終わったらページ 4〜39 と設定ページを読み戻して照合し、最後に工場出荷の PWD (`FF FF FF FF`) で
PWD_AUTH が通ることを確認する (PWD は読み出せず常に 0 が返るため、認証でしか確認できない)。
この最後の認証で失敗しても保護は既に外れているので、タグは使える状態。

### 戻せないもの

**ページ 3 (NDEF の CC)**。NTAG21x の CC は WRITE がビット OR で、立てたビットを落とせない。
アークの CC は `E1 11 12 0F` で、末尾の `0F` は NFC Forum Type 2 Tag の
「読み出し可・書き込み不可」を意味するため、スマホの NFC アプリからは読み取り専用のタグとして
扱われる。メモリ自体は生の WRITE で書けるので、Flipper や生コマンドを使うツールからは
普通に書き換えられる。

消すのは書き込んだ範囲 (ページ 4〜39) だけ。ロックバイトは元から触っていないのでロックはかかって
いない。実物のメダル / アークに使うと、アークごとに固有な NDEF の URL も消えて戻せない
(UI に確認画面を出している)。

## 暗号の実装

FAP からファームの mbedtls は使えない (SDK の api_symbols.csv で非公開) ので、
SHA-256 / HMAC-SHA256 / AES-128 (暗号化方向のみ。CTR なので復号も同じ) を `ym_crypto.c` に実装している。

PC 上でテストできる:

```bash
cc -o test/test_crypto test/test_crypto.c ym_crypto.c && ./test/test_crypto
```

## NFC アプリのプラグイン版 (yokai_medal_parser.fal)

`nfc_plugin/yokai_medal_parser.c` は、標準の NFC アプリに読み取り処理だけを提供する
supported_cards プラグイン。verify/read は `ym_crypto.c` の鍵導出を `.fap` と共有している。

- `verify(nfc)`: ページ 3 を読んで YW3/YW4 のタグか判定する (`.fap` の自動判別と同じロジック)
- `read(nfc, device)`: ページ 0/1 から UID を組み立て、パスワードを計算して
  `mf_ultralight_poller_sync_read_card()` に渡す。NFC アプリ本体が保存を行う
- `parse(device, parsed_data)`: 保存済みのダンプから UID/PWD/チェックサムを表示用テキストにする

複製・種類の変更・書き込み・消去はこちらには実装しない (`.fap` のみ)。

### ビルドが `.fap` と別系統な理由

`.fal` は ufbt (SDK だけ) ではビルドできない。supported_cards プラグインは
`apptype=FlipperAppType.PLUGIN` / `requires=["nfc"]` で、親アプリ `nfc` の `application.fam` が
存在するソースツリー内でないとビルドできず、ufbt の環境には `nfc` アプリのマニフェストが無いため
`Missing application manifest for 'nfc'` で失敗する。

そのため `scripts/build_plugin.sh` が Unleashed ファームウェア全体を shallow clone し、
`applications/main/nfc/plugins/supported_cards/` にこのリポジトリのプラグインを仮配置して、
公式の `fbt` でビルドする。バージョンは既定で Unleashed の最新リリースを
`up.unleashedflip.com/directory.json` の release チャンネルから解決する (`.fap` 側の ufbt と
同じ出どころなので、`.fap` と `.fal` が別バージョン向けになることがない)。
使ったバージョンは `出力先/unleashed_ref.txt` に書き出し、CI が artifact 名に使う。

NFC アプリのプラグイン ABI (`NfcSupportedCardsPlugin` 構造体と verify/read/parse のシグネチャ) は、
Unleashed 本体 (GPL-3.0) のヘッダを複製せず、型定義だけを
`nfc_plugin/nfc_supported_card_plugin_abi.h` として自前で書き起こしている (このリポジトリは MIT)。

タグの種類には依存しない作りになっている (`read()` は `mf_ultralight_poller_sync_read_card()` に
任せ、`parse()` は `ym_data_first_page()` とページ 28〜39 しか見ない) ので、
`.fap` で NTAG215 に書いたタグも、プラグイン側の変更なしで読める (実機で確認済み)。

テストの内容: 妖怪ウォッチ4 の実物のアーク 2 枚のダンプで PWD・復号・チェックサムを確認、
妖怪ウォッチ3 の PWD を別実装 (Python) と比較、複製処理の出力をゲームで読み込めたファイルと比較。
