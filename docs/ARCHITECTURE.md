# 仕組み

## パスワードと暗号の算出

どちらのゲームも、タグの UID (7 バイト) だけから次のように算出している。

```
h1   = HMAC-SHA256(KEY1, UID 7 バイト)
h1'  = h1 の各バイトの上位/下位ニブルを SBOX で置換
h2   = HMAC-SHA256(KEY2, h1')
PWD  = h2[28:32]      … PWD_AUTH (0x1B) で送る 4 バイト
PACK = BE EF          … ゲームが期待する応答
保護データ: AES-128-CTR
  key = h2[0:16]
  IV  = (h2[24:32] || UID || 00) XOR (h2[0:15] || 00)
  48 バイト = 16 バイト x 3 ブロック。各ブロックの最終バイトは先頭 15 バイトの和 (mod 256)
```

| | KEY1 | KEY2 | SBOX | 保護データ |
|---|---|---|---|---|
| 妖怪ウォッチ3 (3DS) | `SjqjE90z8w` | `bYYw75Ks9K` | 14,2,11,7,5,0,12,8,10,13,15,4,6,3,1,9 | ページ 6〜17 |
| 妖怪ウォッチ4 (Switch) | `DKtjn3JAZc` | `5g9D63n8Mt` | 4,9,15,0,5,10,14,1,6,11,13,2,7,12,3,8 | ページ 28〜39 |

妖怪ウォッチ4 の算出式と、ゲーム内部の処理の解析は
[switch-youkaiwatch4-medal](https://github.com/mar1mo-41414/switch-youkaiwatch4-medal) を参照。

### 妖怪ウォッチ4 の平文

先頭 7 バイトが ASCII で `NNNNXXX`。

- `NNNN`: シールに印刷されている番号 (例 `A315` → `0315`)。`int(XXX, 36) − 28652` と一致する。ゲームは使っていない
- `XXX`: アークの種別 ID (36 進 3 文字)。ゲームはこれでアークの種類を決める

残りは 0 (とチェックサム)。

## 種類の自動判別

認証の前にページ 0〜3 を読み、ページ 3 で判別する。

- `F5 10 ..` → 妖怪ウォッチ3 のメダル (ページ 4 は `BABO`)
- `E1 ..` (NDEF の Capability Container) → 妖怪ウォッチ4 のアーク

## 読み取りの流れ

`nfc_poller` (MfUltralight) を使う。

1. `AuthRequest` イベントで UID を取得し、(Auto のとき) `mf_ultralight_poller_read_page(0)` で種類を判別
2. パスワードを計算して `auth_context.password` にセット
3. poller が全ページを読む → `ReadSuccess` で結果をコピー
4. 保護データを復号してチェックサムを確認
5. PWD / PACK をページ 43 / 44 に書き込んでから `nfc_device_save` で保存
   (標準の NFC アプリでパスワードを入れて解除・保存したファイルとバイト単位で同じになる)

## 複製・種類の変更

1. 復号した平文を用意する (Change ID のときは `NNNNXXX` + 0 で作り直す)
2. 新しい UID = `04` + 乱数 6 バイト
3. ページ 0〜2 の UID / BCC0 (`88 ^ UID0 ^ UID1 ^ UID2`) / BCC1 (`UID3 ^ .. ^ UID6`) を書き換え
4. チェックサムを付けて、新しい UID の鍵で暗号化し直す
5. PWD / PACK を書き込んで保存

NDEF の URL と NXP の署名 (READ_SIG の値) は元のまま残す。妖怪ウォッチ4 はどちらも確認していない
(実機で確認済み)。

## 空の NTAG への書き込み

タグの UID は書き換えられないので、**かざしたタグの UID で鍵・PWD を算出し直してから**書き込む
(選んだ `.nfc` の UID は使わない)。1 枚の `.nfc` から UID の違うタグを何枚でも作れる。

`nfc_poller` の `AuthRequest` イベントの中で (= タグが起きていて、poller がまだ全ページ読み取りを
始めていない状態で) 一連の処理を同期的に行う。`mf_ultralight_poller_write_page()` /
`mf_ultralight_poller_read_page()` / `mf_ultralight_poller_auth_pwd()` はコールバックの中からしか
呼べないため。読み取り側の自動判別が同じ場所で `read_page` を使っているのと同じ理屈。

1. タグの種類が NTAG213 / 215 / 216 のどれかを確認する (`writable_tag_type`)。
   UID は 7 バイトであること
2. ページ 0〜3 を読んで静的ロックバイト (ページ 2 の 3・4 バイト目) を確認。
   このページ 0〜3 は書き込む内容の土台にも使う
3. 設定ページを読む。読めない、または AUTH0 が PACK のページ以下 = 既に保護範囲に入っているなら、
   この UID から算出した PWD で解除を試す (このアプリで書いたタグなら通る)。
   動的ロックバイトも確認する
4. 書き込む内容を `app->out` に組み立てる (`build_write_data`)。土台はかざした実タグ
   (種類・バージョン・署名・ページ数・UID) で、そこに元ダンプのページ 3〜39 を載せ、
   保護データはそのタグの UID の鍵で暗号化し直す。PWD / PACK / 設定は、そのタグの種類の位置に置く
5. 書き込む: ページ 3〜39 → PWD → PACK → ACCESS → **CFG0 (AUTH0) を最後**。
   AUTH0 を先に書くと以降のページが保護されて PWD も設定も書けなくなる
6. 書いた PWD で PWD_AUTH して PACK (`BE EF`) を確認し、ページ 3〜39 と設定ページを読み戻して照合
7. 成功したら `app->out` を `app->data` に引き継ぎ、書き込んだ内容と同じダンプを
   `SD:/nfc/yokai/` にも保存する

### タグの種類ごとのページ

保護データ (ページ 3〜39) の位置はどの種類でも同じだが、設定・PWD・PACK・動的ロックの位置は違う。
ページ番号はファームの `mf_ultralight_get_config_page_num()` / `_get_pwd_page_num()` から取る。

| 種類 | 総ページ | CFG0 | ACCESS | PWD | PACK | 動的ロック |
|---|---|---|---|---|---|---|
| NTAG213 | 45 | 41 | 42 | 43 | 44 | 40 |
| NTAG215 | 135 | 131 | 132 | 133 | 134 | 130 |
| NTAG216 | 231 | 227 | 228 | 229 | 230 | 226 |

実物のメダル / アークは NTAG213 だが、**NTAG215 は実機で確認済み** (書き込み → 読み戻し照合 →
標準の NFC アプリ + `.fal` での読み取り・復号 → 妖怪ウォッチ4 での読み込みまで成功)。
NTAG216 はページ構成が NTAG215 と同じなので同様に動くはずだが未検証 (結果画面に注記を出す)。

NTAG215/216 ではメダルが使わないページ 40 以降は空のまま残す。NTAG213 ではそこが設定ページなので、
ゲームが読むページ 0x00〜0x2A のうち 40〜42 だけが NTAG213 と違うことになるが、
ゲームがこの領域を参照していないことは実機で裏付けられた (解析どおり)。

### 書き換えないもの

ページ 0〜2 (UID / BCC / 静的ロックバイト) と動的ロックバイトのページ。ロックをかけないので
同じタグに何度でも書き直せる。`CFGLCK` (設定ページの永久ロック) も立てない。
NXP の署名は空タグのものが残るが、妖怪ウォッチ4 は READ_SIG を送らないので問題にならない。

ページ 3 (NDEF の CC) は WRITE がビット OR になるタグがあるので、「今の値 + 元ダンプの値」を
書き込む値 = 期待値として扱う。こうすると OR のタグでも普通に上書きされるタグでも結果が同じになり、
読み戻しの照合がそのまま使える。工場出荷の NTAG215 (CC = `E1 10 3E 00`) ではサイズのバイトが
`0x3E` のまま残るが、種類の判別 (先頭が `E1`) もゲームの動作も NDEF を見ないので影響しない。

## 暗号の実装

FAP からファームの mbedtls は使えない (SDK の api_symbols.csv で非公開) ので、
SHA-256 / HMAC-SHA256 / AES-128 (暗号化方向のみ。CTR なので復号も同じ) を `ym_crypto.c` に実装している。

PC 上でテストできる:

```bash
cc -o test/test_crypto test/test_crypto.c ym_crypto.c && ./test/test_crypto
```

## NFC アプリのプラグイン版 (yokai_medal_parser.fal)

`nfc_plugin/yokai_medal_parser.c` は、標準の NFC アプリに読み取り処理だけを提供する
supported_cards プラグイン。verify/read は `ym_crypto.c` の鍵導出を `.fap` と共有している。

- `verify(nfc)`: ページ 3 を読んで YW3/YW4 のタグか判定する (`.fap` の自動判別と同じロジック)
- `read(nfc, device)`: ページ 0/1 から UID を組み立て、パスワードを計算して
  `mf_ultralight_poller_sync_read_card()` に渡す。NFC アプリ本体が保存を行う
- `parse(device, parsed_data)`: 保存済みのダンプから UID/PWD/チェックサムを表示用テキストにする

ビルドは `.fap` と別系統 (`scripts/build_plugin.sh`)。理由は README を参照。
複製・種類の変更・書き込みはこちらには実装しない (`.fap` のみ)。

タグの種類には依存しない作りになっている (`read()` は `mf_ultralight_poller_sync_read_card()` に
任せ、`parse()` は `ym_data_first_page()` とページ 28〜39 しか見ない) ので、
`.fap` で NTAG215 に書いたタグも、プラグイン側の変更なしで読める (実機で確認済み)。

テストの内容: 妖怪ウォッチ4 の実物のアーク 2 枚のダンプで PWD・復号・チェックサムを確認、
妖怪ウォッチ3 の PWD を別実装 (Python) と比較、複製処理の出力をゲームで読み込めたファイルと比較。
